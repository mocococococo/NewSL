# 複数PCでの学習データ生成

このPCがチャンク割り当て・状態確認・回収・学習・モデル頒布を制御します。
遠隔PCは、このPCからSSHで起動された生成処理を実行して、自分の状態を記録します。
遠隔PCからこのPCへ指示を出す処理はありません。

## ファイルごとの役割

| ファイル | 責務と実行場所 |
|---|---|
| `shot_pipeline.py` | このPCで起動する全体制御。チャンク割り当て、ローカル・遠隔の同時生成、確認タイミング、回収後の状態変更の指示、学習、Gitによるモデル頒布、次のend／shotへの移行を担当します。 |
| `remote_status.py` | 実行されたPCの`remote/state.json`を読み、プロセスの生存情報とともにJSONで返します。ファイルを作成・更新しません。 |
| `remote_generate.py` | 実行されたPCで、引数として渡された1チャンクを生成します。自分のワーカーの開始・完了・結果を記録します。生成元コード・入力ログ・モデルの一致確認も行います。回収・学習・モデル頒布は行いません。 |
| `remote_collect.py` | このPCで、指定された生成結果をSFTPでコピーし、サイズとSHA-256を確認します。状態変更や次の割り当てを判断しません。 |
| `ssh_connection.py` | このPCで使う通信共通処理。IP登録JSONの読み取り、SSH接続、指定コマンドの実行、SFTP接続を提供します。生成条件や次の処理を判断しません。 |
| `state_store.py` | 各PCの状態保存の共通処理。JSON読み書き、排他制御、ワーカー初期化、回収済み通知の反映、明示的な失敗状態の解除を担当します。パス・ハッシュ・プロセス識別の低水準関数もここにあります。 |
| `config.jsonc` | このPCで実際に読み込むコメント付き運用設定です。各項目の直前に意味・単位・注意点を記載しています。サンプル用の名前や別の標準設定ファイルはありません。 |
| `config_loader.py` | 設定読み込み専用の共通処理。JSONCのコメントを文字列と区別して読み込みます。通常起動と手動回収で共通利用し、設定値の変更や通信は行いません。 |
| `__init__.py` | `remote_generate`をPythonパッケージとして扱うためのファイルです。単独で起動しません。 |
| `requirements.txt` | このPCに必要な追加ライブラリ`paramiko`、`python-dotenv`の一覧です。 |
| `README.md` | この説明書です。 |

通常、手動で起動するのはこのPCの`shot_pipeline.py`だけです。
他のプログラムはパイプラインが関数またはSSH経由で呼び出します。
既存の`transformer/shot_generator.py`の生成関数と、
`transformer/shot_pipeline.py`の学習ステージを再利用しています。
既存の単一PC用プログラムは変更していません。

## 設定と状態の保存先

```text
NewSL/
├─ remote_generate/   # プログラムとconfig.jsonc
├─ remote/
│  └─ state.json      # そのPCの全ワーカーの状態
├─ data/
│  └─ endX/shotY/sl_data_chunkN_*.npz
├─ model/
│  └─ shot-endX-shotY.bin
└─ log/
   └─ remote-worker-N.log
```

`config.jsonc`は人が編集する設定です。パイプラインが起動時に読みます。
`// 行コメント`と`/* ブロックコメント */`を使用できます。末尾カンマは使用できません。
文字列内の`//`や`/*`はコメントとして扱いません。コメントだけの変更は再開時の設定一致判定に影響しません。
旧`config.json`から設定値を維持して改名しました。標準の読み込み先は`config.jsonc`です。
遠隔の生成プログラムは設定ファイルを読みません。このPCから渡された生成条件を使います。
パスワードは`env_file`で指定した`.env`、または同名の環境変数から読みます。
環境変数を優先し、設定JSON・状態JSONにパスワードは保存しません。

実行状態は**各PCにつき`remote/state.json`の1ファイル**です。
このPCでは、同じファイルの`pipeline`にチャンクの割り当て・回収状況・学習段階も保存します。
ジョブごとのJSON、常駐サーバー用の別状態ファイル、永続的なロックファイルは作りません。
原子的な更新用の`.state.<ID>.tmp`と転送用の`.<ファイル名>.<ID>.part`は一時ファイルです。
通常は処理後に消えますが、OSやプロセスが強制終了すると残る場合があります。

## config.jsoncの設定項目

起動引数は`--config`と`--resume`のみです。数値などの運用パラメータを起動引数へ重複定義していません。
未知の設定キーや不足したキーはエラーにします。

| 設定箇所 | 内容 |
|---|---|
| `gateway` | 中継サーバーのホスト名、ユーザー名、秘密鍵とknown_hostsの場所。 |
| `local` | このPCの識別名、ワーカー数、ワーカーあたりのCPUスレッド数、入力ログの場所。 |
| `remotes` | 各遠隔PCの識別名、並列数、CPUスレッド数、リポジトリの絶対パス、Python実行ファイル、認証・IP登録JSON・入力ログの場所。PCを増やす場合は配列へ追加します。 |
| `control.poll_seconds` | PCごとの状態確認後に待つ秒数。標準5秒。通信時間もかかるため、厳密な固定周期ではありません。全PC共通です。 |
| `control.connection_retries` | SSH通信失敗時の追加再試行回数。標準12回。 |
| `control.retry_seconds` | 通信再試行までの待ち時間。標準5秒。 |
| `control.start_grace_seconds` | 起動指示後、状態がまだidleのときに、同じジョブの起動を再指示するまでの猶予。標準30秒。 |
| `control.start_attempts` | 状態に開始が記録されないときの起動指示回数の上限。標準3回。 |
| `transport` | 接続・SFTP入出力・SSHコマンドの各タイムアウト秒数。コマンドの標準は300秒で、事前照合やモデルのpullにも適用します。 |
| `generation.start_end/start_shot/stop_end/stop_shot` | end9/shot15からend0/shot0へ逆順に進む範囲。終了位置も含みます。 |
| `generation.chunk_start/chunk_end` | 各局面で生成するチャンクの範囲。終了番号も含みます。**初期設定は0〜7の8チャンク**です。実際に必要な範囲へ変更してください。 |
| `generation.chunk_size` | チャンクごとの入力ログ数。標準1024。NPZに保存するサンプル数の設定ではありません。 |
| `generation.search_mode/base_model` | 探索モードとベースモデル。初期設定はshotです。モードは既存の`search_config.py`と一致させる必要があります。 |
| `generation.data_size/shuffle_seed/simulation_seed/inference_batch_size/max_simulations` | チャンクごとの処理ログ数上限、入力の並び順のシード、探索シード、推論バッチサイズ、探索回数。data_sizeは学習サンプル数の指定ではありません。 |
| `generation.use_*_augmentation` | endと得点差の拡張の有無。 |
| `generation.policy_*/value_*` | 既存生成関数へ渡す教師分布作成のパラメータ。 |
| `training.batch_size/epochs` | このPCで学習するときのバッチサイズとエポック数。標準1024・50。 |
| `git.remote` | モデルをpush／pullするGitリモート名。標準origin。ブランチは開始時のブランチを使います。 |

このファイルへ集約したのは、分散パイプラインから指定する運用条件と生成関数の引数です。
既存ネットワークの構造、探索モードの定義、学習器内部のオプティマイザー・学習率・NPZの保存単位は、
既存コードと`search_config.py`・`learning_param.py`の設定を使用します。
これらまで新しいJSONへ移す変更は行っていません。

## 実行前の準備

1. 今回の`remote_generate/`を含むコードをコミットし、各PCを同じブランチ・同じコミットに揃えます。未コミットのPythonコードで開始しません。これらの初回配布は自動学習ループの開始前に行います。
2. 各PCに既存の生成・学習環境とCUDAを用意します。Pythonのmajor/minor、PyTorch、NumPyのバージョンを揃えます。このPCには`requirements.txt`の追加ライブラリも必要です。
3. `config.jsonc`の生成範囲、PCごとのパス、並列数を確認します。遠隔PCはWindowsを対象とし、PowerShellとSSH環境から指定のPythonを実行できる必要があります。
4. 各PCへ同じ入力ログとベースモデルを事前配置します。開始shotが15未満なら、同じendのshot+1の教師モデルも必要です。入力ログとベースモデルの初回コピーは、このパイプラインの対象外です。
5. `.env`の`PC_PASSWORD`、中継用秘密鍵、既に確認済みのknown_hostsを用意します。遠隔PCのknown_hostsは、変更されるIPではなく`remote-01`などのPC識別名で確認します。
6. 中継サーバーの`/home1/y2025/k2531031/research/remote-01.json`へ現在のVPN IPが登録されていることを確認します。既存の`publish_vpn_ip.py`による手動登録を使います。VPN変更の自動監視・自動登録はこの実装に含みません。
7. このPCからGitへpush、各遠隔PCからGitへpullできる認証を用意します。遠隔側に追跡ファイルの未コミット変更があるとpull前に停止します。
8. 新規実行対象の各end／shotに、以前の生成NPZや出力モデルが残っていないことを確認します。既存データを混ぜたり自動削除したりせず、見つけた場合は開始前に停止します。

`remote/state.json`がなければ、実際の起動時に初期化します。
既に存在する場合は`schema_version: 1`、`pc_id`、`workers`配列を必要とします。
既存の動作中・未回収のワーカーを勝手にidleへ戻しません。

## 通常の起動

リポジトリのルートで、このPCから実行します。

```powershell
python -m remote_generate.shot_pipeline
```

別の設定ファイルを明示する場合は次の形です。

```powershell
python -m remote_generate.shot_pipeline --config remote_generate/config.jsonc
```

設定の初期値では、このPCで4プロセス、遠隔PCで4プロセスが同時に生成します。
各生成プロセスへ1チャンクを渡し、内部の生成関数には`num_workers=1`を指定します。
処理が早く終わったワーカーへ、このPCが残りのチャンクを順次割り当てます。

## 状態遷移と回収

```text
idle → running → completed → 回収確認済みの通知 → idle
```

`completed`は生成処理が終了した状態です。結果の`success`で成功・失敗を区別します。
成功時は`files`にパス・サイズ・SHA-256・サンプル数が入ります。
失敗時は`success: false`と`error`を記録し、パイプラインが新規割り当てを停止します。
強制終了でrunningのまま残った場合も、状態取得時のプロセス生存確認によって停止します。

このPCは割り当てを自身のstate.jsonへ保存してから生成を起動します。
遠隔側の生成プロセスはSSHセッションから分離して起動します。
SSHサーバー側がその分離を許可しない場合は、起動エラーになります。
通信切断で起動の成否が不明でも、同じジョブIDを使い、別PCへ二重割り当てしません。

各PCの状態を1回取得し、そのPCの全ワーカーで結果を共有します。
回収処理は別の非同期タスクで進めるため、回収中も状態確認と他ワーカーの生成を続けます。
生成データは中継SSH接続上のSFTPを使い、遠隔の`data/endX/shotY/`からこのPCの同じ相対パスへコピーします。
中継サーバーへデータファイルを置く処理はありません。

コピーは一時ファイルへ行い、サイズとSHA-256が一致してから最終名へ確定します。
同じ内容の取得済みファイルは再利用し、異なる内容の同名ファイルは上書きしません。
転送途中のファイルについて、バイト位置からの転送再開は行わず、再試行時は先頭から取得します。
**遠隔の元データは削除しません。**

回収成功をこのPCのstate.jsonへ保存してから、パイプラインが遠隔のstate_storeへackを指示します。
ackは対象のワーカーとジョブIDを照合してidleへ戻します。
その後に次のチャンクを割り当てます。未割当がなくなっただけでは学習を始めません。
全チャンクの生成・回収が成功し、保存先に不足・混入がないことを確認してから学習します。
保存対象のサンプルが0件のチャンクは正常終了できますが、全体が空なら学習前に停止します。

## 学習とモデル頒布

学習はこのPCだけで行います。モデルは`model/<mode>-endX-shotY.bin`へ保存します。
パイプラインは、そのモデルだけを`git add`、`git commit --only`し、設定されたGitリモートへpushします。
コミットメッセージは`モデルendX, shotY 追加`です。生成データ、state.json、設定変更、学習記録はこのコミットへ含めません。

push成功後、このPCがSSH経由で全遠隔PCへ`git pull --ff-only`を指示します。
全ワーカーがidleであること、公開したコミットに到達したこと、モデルのSHA-256とPythonコードの一致を確認します。
全遠隔PCで確認できるまで次の局面に進みません。モデル本体はGit経由で転送されます。

次のend／shotと使用する教師モデルは、このPCが次の生成指示に含めます。
生成プログラムの書き換え・再コミットは不要です。
実行途中でのPythonコード変更や、パイプライン外でのコミット追加は停止要因になります。

## 中断・再開と失敗時の扱い

```powershell
python -m remote_generate.shot_pipeline --resume
```

このPCのstate.jsonに保存した段階から再開します。
生成・学習条件とPC構成は同じものが必要です。
`control`と`transport`の待ち時間・再試行条件は、停止後に設定を変えて再開できます。
実行中の設定ファイルの変更は自動反映しません。

通信失敗は設定回数まで再試行し、接続のたびに中継JSONからIPを読み直します。
認証失敗、異なるファイルの検出、生成の失敗は通信再試行で隠しません。
停止しても他の生成プロセスが残ることがあります。状態とログを確認してください。
同じこのPCのリポジトリで、パイプラインを二重起動することは拒否します。

生成失敗やプロセス消失時は自動再生成しません。
原因を直し、**対象ジョブの生成プロセスが終了したことを確認し、そのチャンクの不完全なNPZを整理した後**、
対象PCで次のように状態を明示的に解除できます。コマンド自体はデータを削除しません。

```powershell
python -m remote_generate.state_store reset --pc-id remote-01 --worker-id worker-0 --job-id <対象ジョブID>
```

生存中のプロセスや正常完了した結果はresetできません。
解除後、このPCで`--resume`すると同じ担当チャンクを再実行します。
起動自体に失敗してidleのまま上限に達した場合は、ログで原因を直し、
`control.start_attempts`を増やして再開できます。
学習段階で中断した場合は、その局面の学習を最初からやり直します。
頒布段階で停止した場合は、同じモデルのpush／pullと確認をやり直します。

## 個別の確認・回収

遠隔PCで状態を取得するコマンドです。ファイルを変更しません。

```powershell
python -m remote_generate.remote_status --pc-id remote-01
```

このPCから手動で回収する場合は次の形です。

```powershell
python -m remote_generate.remote_collect --pc-id remote-01 --worker-id worker-0 --job-id <対象ジョブID>
```

手動回収はコピーと確認だけを行い、ackや次の割り当ては行いません。
パイプラインを再開すると既存の同一ファイルを確認してから、通常の回収済み通知を行います。

## 今回の確認範囲

コードの読み取り、Pythonと埋め込みスクリプトの構文解析による静的確認を行いました。
JSONC対応では、設定読み込み処理だけを単体で確認し、コメント・文字列・不正な構文の扱いと、改名前後の設定値の一致を確認しました。
生成プログラム・パイプラインの実行、SSH接続、実データの転送、学習、Gitのcommit／push／pullは実施していません。
実機での動作は未検証です。特にWindows SSHからのプロセス分離と、モデル頒布を含む一連の動作は実行確認が必要です。
